## Phase 1 — Product Audit

### Objective
Before adding new features, perform a complete audit of v1.0 to identify where real technical debt exists (not to "refactor everything").

### Specs — Backend
Areas to review: endpoints, input validation, error handling, authorization, data isolation between users, Prisma queries, query performance, PostgreSQL indexes.

### Specs — Frontend
Areas to review: loading states, empty states, error states, responsive design, navigation, basic accessibility.

### Specs — Code
Areas to review: dead code, old TODOs, duplication, naming, excessively large modules, documentation, outdated dependencies.

### Tasks — Backend
- [x] Review all existing endpoints (naming and contract consistency)
- [x] Review input validation on each endpoint
- [x] Review error handling (format and HTTP status consistency)
- [x] Review authorization logic on every protected route
- [x] Confirm data isolation between users across all entities
- [x] Review all existing Prisma queries
- [x] Identify unnecessarily heavy queries (N+1, excessive joins, etc.)
- [x] Review existing PostgreSQL indexes and identify missing ones

### Audit findings — Backend

Consolidated, prioritized list of technical debt identified in the backend audit (v1.0). Decisions: **fix in this version** vs **deferred**.

| ID | Finding | Severity | Decision |
|----|---------|----------|----------|
| B1 | `POST /auth/register` returned 200 instead of 201 | Low | ✅ Fixed |
| B2 | Inconsistent response shape across `/stats/*` (unwrapped vs `{ stats }`) | Medium | ✅ Fixed — all stats endpoints now return `{ stats }` |
| B3 | Divergent error-return conventions across services (`null` / `{ success }` / `{ error, status }`) | Medium | ✅ Fixed — uniform `{ resource } \| { error, status }` and `true \| { error, status }` |
| B4 | `pillarId` validated as plain string, not UUID | Low | ✅ Fixed — `z.uuid()` |
| B5 | Duplicated manual `safeParse` boilerplate across ~12 route handlers | Medium | ✅ Fixed — shared `validateInput()` helper (`apps/api/src/lib/validation.ts`) |
| B8 | Redundant `@@index([habitId, date])` duplicating the unique constraint index | Low | ✅ Fixed — removed + migration |
| B6 | `getHabitStats` / `getHabitStatsList` load full completion history without date filter | Medium | ⏳ Deferred — Phase 4 (Analytics 2.0) |
| B7 | `getMonthlyStats` filters in JS with O(days × completions) + O(habits × completions) | Medium | ⏳ Deferred — Phase 4 (Analytics 2.0) |
| B9 | `/stats/overview` fires ~6+ queries (3 sub-endpoints) | Medium | ⏳ Deferred — Phase 4 (Analytics 2.0) |

Areas reviewed with **no issues found**: authorization on all protected routes (`requireAuth`), user data isolation across all entities (verified + covered by tests), error response format (consistent `{ error }`, no internal leakage), N+1 queries (none found).

### Tasks — Frontend
- [ ] Review all existing loading states
- [ ] Review all existing empty states
- [ ] Review all existing error states
- [ ] Review responsive behavior across all pages
- [ ] Manually test on desktop
- [ ] Manually test on mobile
- [ ] Test across different screen sizes (breakpoints)
- [ ] Review the app's global navigation
- [ ] Review basic accessibility (contrast, labels, keyboard navigation)

### Tasks — Code
- [ ] Remove identified dead code
- [ ] Remove old TODOs already resolved or irrelevant
- [ ] Identify and document relevant code duplication
- [ ] Review inconsistent naming of variables, functions, and files
- [ ] Identify excessively large modules that are candidates for splitting
- [ ] Update outdated technical documentation
- [ ] Review outdated or unused dependencies

### Completion criteria
A consolidated, prioritized list of real technical debt exists (backend, frontend, and code), with an explicit decision on what will be fixed in this version and what is deferred.

## Phase 3 — More Complete Habit System

### Objective
Evolve the habit core (already proven in the MVP) to support more realistic frequencies and richer history.

### Specs — Frequencies to support
```text
Daily
Specific days of the week
X times per week
X times per month
```

Examples:
```text
Train        → 4 times / week
Read         → Every weekday
Program      → Every day
```

### Specs — Architecture rule
Before changing the database model, formally document:
```text
Expected completions
Actual completions
Completion rate
```
for each frequency type, since this directly changes the definition of "completion rate" used in statistics.

### Specs — History
- Full history per habit.
- Individual calendar per habit.
- Current streak.
- Best streak.
- Completion rate.
- Comparison between periods.

Example:
```text
Programming
Current streak: 12 days
Best streak: 31 days
30-day completion: 87%
```

### Tasks
- [ ] Formally document the "expected completions" definition for each frequency type
- [ ] Update the `Habit` model in Prisma to support frequency (type + parameters)
- [ ] Create a migration for the new frequency field (with a default value = daily, to avoid breaking existing habits)
- [ ] Implement "expected completions" calculation logic per frequency type
- [ ] Update habit creation/edit endpoints to accept frequency
- [ ] Update the habit creation/edit frontend with frequency selection
- [ ] Update completion rate calculation to account for the habit's frequency
- [ ] Implement an individual history page/section per habit
- [ ] Implement an individual calendar per habit (monthly view)
- [ ] Implement current streak calculation accounting for frequency
- [ ] Implement best streak calculation accounting for frequency
- [ ] Implement comparison between periods (e.g., last 30 days vs. previous 30 days)
- [ ] Write tests for the new completion rate and streak calculations across different frequencies
- [ ] Migrate existing (dogfooding) habits to the new model without data loss

### Completion criteria
Habits can be configured with realistic frequencies (daily, specific days, X times per week/month), and all completion rate and streak metrics correctly reflect the configured frequency.

## Phase 5 — Goals

### Objective
Introduce the concept of "an outcome I want to achieve," bringing LifeOS closer to the idea of "building a life" instead of just checking off habits.

### Specs — Conceptual model

```text
Pillar
   ↓
Goal
   ↓
Habit
```

Example:
```text
Engineering

Goal: Become a better software engineer
Progress: ████████░░ 80%

Supporting habits:
✓ Program every day
✓ Study architecture
✓ Read documentation
```

### Specs — Scope (what NOT to include yet)
No OKRs, complex milestones, or sophisticated scoring systems in this phase.

### Tasks
- [ ] Design the `Goal` data model (id, userId, pillarId, title, description, deadline, status, progress)
- [ ] Create the `Goal` model in Prisma and run the migration
- [ ] Define and document the possible `status` values (e.g., active, completed, abandoned)
- [ ] Define how `progress` is calculated (manual vs. derived from associated habits)
- [ ] Implement the association between `Goal` and `Habit` (N:N relation or join table)
- [ ] Implement `Goal` CRUD endpoints (`GET/POST/PATCH/DELETE /goals`)
- [ ] Implement an endpoint to associate/disassociate habits with a goal
- [ ] Write backend tests for goal CRUD and association rules
- [ ] Create a Goals listing page (grouped by pillar)
- [ ] Create a Goal detail page, with progress and associated habits
- [ ] Implement Goal creation/editing in the frontend (title, description, deadline, pillar)
- [ ] Implement associating habits with a Goal in the interface
- [ ] Implement Goal progress history over time
- [ ] Test the full flow: create goal → associate habits → watch progress evolve with completions

### Completion criteria
The user can create Goals associated with Pillars, link them to existing Habits, and view the Goal's progress consistently with the actual completions of the associated habits.

## Phase 7 — Daily Journal / Life Logs

### Objective
Introduce daily logging of subjective state (mood, energy, sleep, notes), without relying on AI, allowing this data to be cross-referenced with habit completion history.

### Specs — Daily Log
```text
Daily Log
Mood
Energy
Sleep
Notes
```

### Specs — Scope rule
Explicitly keep this feature AI-free at this stage.

### Specs — Data cross-referencing (example)
```text
Average completion rate:

Days with <6h sleep    → 68%
Days with 7–9h sleep   → 87%
```

Important: these correlations must be presented as **association**, never as causation.

### Tasks
- [ ] Design the `DailyLog` data model (id, userId, date, mood, energy, sleepHours, notes)
- [ ] Create the `DailyLog` model in Prisma and run the migration (with a uniqueness constraint on `userId` + `date`)
- [ ] Implement `DailyLog` CRUD endpoints (`GET/POST/PATCH /daily-logs`)
- [ ] Write backend tests for daily log CRUD
- [ ] Create a daily logging page/section (form with mood 1–10, energy 1–10, sleep, notes)
- [ ] Implement daily log history
- [ ] Implement a calendar view of daily logs
- [ ] Implement an endpoint correlating daily logs with completion rate (e.g., sleep vs. completion rate)
- [ ] Implement the display of these correlations in the frontend, with explicit association (not causation) language
- [ ] Test the full flow: log daily entry → mark habits → see the correlation reflected over time

### Completion criteria
The user can log mood, energy, sleep, and notes daily, view the history, and view correlations with habit completion rate, always presented as association rather than causation.

## Phase 9 — Gamification / Progression

### Objective
Introduce progression (XP/Level) only once there is enough raw material (Habits, Goals, Projects, Pillars, Analytics, History) for progression to be meaningful rather than arbitrary.

### Specs — Progression structure
```text
Pillar XP
Pillar Level
Overall Level
```

Example:
```text
ENGINEERING
Level 18
████████░░
8,240 / 10,000 XP
Rank: B
```

### Specs — Transparency rule
The XP formula must be transparent and derived from real progress:
```text
Habit completion
       +
Goal progress
       +
Project progress
       +
Consistency
       ↓
Pillar XP
```

Explicit rule: gamification must **represent real progress**, never fabricate progress (e.g., no "+500 XP" for checking an isolated box unrelated to actual effort).

### Tasks
- [ ] Formally document the XP calculation formula per pillar (weights for habit completion, goal progress, project progress, consistency)
- [ ] Validate the formula against real dogfooding data before implementing
- [ ] Design the data model to store XP/Level per pillar and overall
- [ ] Implement the XP calculation as a derived value (not stored directly, or recalculated in an auditable way)
- [ ] Implement an endpoint to query XP/Level per pillar and overall
- [ ] Define the level progression curve (e.g., XP required per level)
- [ ] Define the "Rank" system (if applicable) and its criteria
- [ ] Implement XP/Level visualization per pillar in the frontend
- [ ] Implement Overall Level visualization
- [ ] Write tests for XP calculation across different progress combinations
- [ ] Validate with the user (dogfooding) whether the progression "feels" fair and representative

### Completion criteria
An XP/Level system exists per pillar and overall, with a documented and transparent formula, validated against real data, representing genuine progress rather than an arbitrary metric.

## Philosophy Shift: MVP vs. Intermediate Product

In the MVP, the success criterion was:

> **"Does it work?"**

In v1.5, the criterion becomes:

> **"Can someone who isn't me understand, use, and trust this?"**

This is the real transition between MVP and intermediate product.

### Discipline to maintain during development

There is a natural temptation at this point: "the MVP is ready, so now I can finally build all the ideas I've had." This temptation should be resisted.

The MVP provided something more valuable than the feature list itself: **over the coming weeks, the user themself becomes the source of requirements for LifeOS.**

Practical rule:
- If a problem shows up repeatedly during daily use → it goes into the backlog.
- If a feature seems interesting but doesn't solve any real problem encountered → it stays out.

This discipline is what turns LifeOS from a project that works into a product worth showing.
