# LifeOS v1.6 — Account Security, Lifecycle & i18n

> A lean, focused roadmap covering four specific but high-impact improvements: a strong password policy, account management (email verification, password recovery, password/email changes), account soft-delete with a 15-day recovery window, and a production-ready internationalization (i18n) system.
> Unlike the previous roadmaps (MVP, v1.5, Improve), this one doesn't cover the whole product — it's a surgical cycle over specific but particularly sensitive areas.
> Each phase includes: **objective**, **description/specs**, and **completion tasks** (checklist).

---

## A Note on Versioning

This release should be treated as **`v1.6.0`**, not as a patch (`v1.5.2`).

In [Semantic Versioning](https://semver.org/), the `PATCH` version (the third number) is reserved for bug fixes that don't change the application's observable behavior. The `MINOR` version (the second number) is for new, backward-compatible functionality that users can actually notice.

Everything in this roadmap clearly falls under `MINOR`:

- Email verification, password recovery, email change, and account soft-delete are **entirely new flows** that don't exist today.
- The stronger password policy **changes validation behavior** (passwords that used to be accepted are now rejected) — that's not a bugfix, it's a business rule change.
- The i18n system is a **new capability** across the entire interface.

## Phase 1 — Strong Password Policy

### Objective
Replace the current password validation (likely just a "minimum length") with a real security policy, applied consistently at every point where a password is set or changed (registration, reset, change).

### Specs — Password rules

```text
Minimum length:           8 characters
Maximum length:           72 characters (bcrypt's practical limit)
Requires:                 1 lowercase letter
Requires:                 1 uppercase letter
Requires:                 1 number
Requires:                 1 special character (!@#$%^&*()-_=+[]{};:,.<>?/...)
Not allowed:               password equal to the user's email
Not allowed:               password among the N most common (e.g., rockyou top 1000 list)
```

Important technical note: **bcrypt** (used for password hashing) silently ignores any character past byte 72. Without an explicit maximum length, a 200-character password would be "accepted" but only the first 72 bytes would actually count — this must be validated explicitly to avoid a false sense of security.

### Specs — A single rule, applied at every entry point
Validation must live in **one single place** in `packages/shared` (a Zod schema), reused by:
- Registration (`POST /auth/register`)
- Password reset (Phase 4)
- Password change (Phase 5)

This avoids the scenario where a weak password is rejected at registration but silently accepted during a reset.

### Specs — Frontend
- Real-time password strength indicator (weak / medium / strong), computed locally as the user types.
- List of requirements with immediate visual feedback (✓/✗) per rule (e.g., "✓ 8+ characters", "✗ 1 number").
- Never log the password or send it to any kind of analytics/telemetry.

### Tasks
- [x] Formally define the password rules in `packages/shared` (a single Zod schema)
- [x] Add maximum length validation (72 bytes) with a clear error message
- [x] Add a list of forbidden common passwords (e.g., rockyou top 1000, bundled or loaded locally — no external calls)
- [x] Prevent a password equal to the user's email
- [x] Update `POST /auth/register` to use the new shared schema
- [x] Write table-driven tests covering every rule (accept valid ones, reject each violation individually)
- [x] Update the registration form on the frontend with a real-time strength indicator
- [x] Implement a visual requirements checklist (✓/✗ per rule) in the form (How it is currently done)
- [x] Add a show/hide password toggle
- [x] Audit the code to confirm the password is never logged, even on errors
- [x] Update the API documentation (password validation error contract)

### Completion criteria
A single shared password schema exists, applied consistently across every endpoint that sets passwords, with tests covering each rule individually, and the frontend gives clear, real-time feedback on password strength.

## Phase 2 — Transactional Email Infrastructure

### Objective
Build the email-sending infrastructure that will support Phases 3 through 6 (verification, password recovery, email change, soft-delete). This phase is deliberately placed before the others, since all of them depend on it.

### Specs — Provider choice
Choose **one** transactional email provider (e.g., Resend, Postmark, SendGrid, AWS SES). Criteria to consider: a free tier sufficient for a personal/portfolio project, good deliverability, a simple API, and template support.

> Discipline note (aligned with the "Improve" roadmap): don't build a message queue (e.g., Redis + BullMQ) just for sending emails. A direct, synchronous send with simple retry and failure logging is enough for this project's expected volume. Introducing a queue here would be overengineering.

### Specs — Service abstraction
Create an `EmailService` interface independent of the chosen provider, so that switching providers in the future doesn't require touching any domain code:

```text
EmailService.send({
  to: string,
  template: "verify-email" | "password-reset" | "password-changed" |
            "email-change-request" | "email-change-alert" |
            "account-deletion-requested" | "account-deletion-reminder" |
            "account-deleted",
  data: Record<string, unknown>,
  locale: string
})
```

### Specs — Domain configuration
- Configure SPF, DKIM, and DMARC on the sending domain (e.g., `noreply@lifeos.app`), to avoid emails landing in spam.
- Define a consistent sender and reply-to address.

### Specs — Development environment
- In development, emails should **not** be sent to real inboxes by default. Use the chosen provider's sandbox mode, or a local tool (e.g., Mailhog/Ethereal) to inspect emails sent locally.

### Specs — Templates
- A base HTML template (header, footer, LifeOS branding) reused by every transactional email.
- A plain-text fallback version for each template, for email clients that don't render HTML.

## Phase 3 — Email Verification (Account Confirmation)

> ⚠️ Critical phase. Failures here can lock legitimate users out of their own accounts, or allow ghost/spam accounts. Every step must be explicitly tested, including error cases.

### Objective
Securely confirm that the email provided at registration actually belongs to the user, by sending a real verification link to the inbox.

### Specs — Data model

```prisma
model User {
  // ... existing fields
  emailVerified Boolean @default(false)
}

model EmailVerificationToken {
  id        String   @id @default(uuid())
  userId    String
  tokenHash String   @unique
  expiresAt DateTime
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
}
```

### Specs — Token security rules
- The token sent by email is **random** (e.g., 32 bytes via `crypto.randomBytes`), never predictable.
- Only the **hash** of the token (e.g., SHA-256) is stored in the database — the plaintext token is never persisted.
- Expires in **24 hours**.
- **Single-use**: after successful verification, the token is deleted/invalidated.
- When a new verification email is requested, **all previous tokens for that user are invalidated** (prevents an old token, if compromised, from remaining valid).
- Token comparison done safely — comparing the received hash against the stored hash already mitigates timing-attack concerns, since the compared value is never the plaintext secret.

### Specs — Endpoints

| Method | Route                          | Description                                                |
|--------|---------------------------------|--------------------------------------------------------------|
| POST   | `/auth/verify-email`            | Receives the token, marks `emailVerified = true`               |
| POST   | `/auth/resend-verification`     | Resends the verification email (authenticated or by email)     |

### Specs — Protection against account enumeration
`POST /auth/resend-verification` must **never** reveal whether an email exists or not in the system. Always a generic response:
```json
{ "message": "If an account with that email exists and is not yet verified, a new verification email has been sent." }
```

### Specs — Product decision: block unverified users or not?

**Restricted access:** an unverified user can log in normally, but sees a persistent banner ("Verify your email") and, optionally, some sensitive actions remain blocked (e.g., changing the email, deleting the account) until verified.

### Specs — Rate limiting
- `POST /auth/resend-verification`: aggressive limit (e.g., 3 requests per hour per email/IP), to prevent abuse (spamming emails to third parties).

### Specs — Error cases to handle explicitly
```text
Invalid/nonexistent token             → generic error, no details
Expired token                         → clear message + option to resend
Already-used token                    → clear message ("already verified" if applicable)
Already-verified email                → friendly, idempotent response, no error
Resend request for unregistered email → generic response (no enumeration)
Multiple consecutive resend requests  → rate limit, visible cooldown in the frontend
```

- [x] Implement `POST /auth/resend-verification` with a generic anti-enumeration response

## Phase 4 — Password Recovery

> ⚠️ Critical phase. This is one of the most common attack vectors in any authentication system. Every decision here must prioritize security over convenience.

### Objective
Allow a user who forgot their password to securely regain access to their account, via a unique link sent by email, without ever exposing whether a given email is registered in the system.

### Specs — Data model

```prisma
model PasswordResetToken {
  id        String   @id @default(uuid())
  userId    String
  tokenHash String   @unique
  expiresAt DateTime
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
}
```

### Specs — Token security rules
- Random token (32 bytes), never predictable; only the hash is persisted.
- Expires in **1 hour** — a shorter window than email verification, since a password reset is more sensitive.
- Single-use: invalidated immediately after a successful reset.
- Requesting a new reset invalidates any still-active previous reset token for that user.

### Specs — Endpoints

| Method | Route                     | Description                                              |
|--------|---------------------------|--------------------------------------------------------------|
| POST   | `/auth/forgot-password`   | Receives the email, sends a reset link if the account exists  |
| POST   | `/auth/reset-password`    | Receives the token + new password, updates the password        |

### Specs — Protection against account enumeration
`POST /auth/forgot-password` **always** responds the same way, whether or not the email exists:
```json
{ "message": "If an account with that email exists, a password reset link has been sent." }
```
Response time must also be consistent between "email exists" and "email doesn't exist" (avoid a latency difference acting as an enumeration oracle — e.g., always trigger equivalent hashing/lookup work).

### Specs — Session invalidation after reset
After a successful password reset, **all existing sessions/JWT tokens must become invalid** — including any an attacker might already have had access to. Recommended mechanism: a `passwordChangedAt` field on `User`, checked in the authentication middleware — any JWT issued before that timestamp is rejected, forcing a fresh login on every device.

### Specs — Security notification
After a successful reset, send a confirmation email ("Your password was changed. If this wasn't you, contact us immediately.") — even if the user themself made the request, this notification acts as a safety net in case the account was compromised.

### Specs — Rate limiting
- `POST /auth/forgot-password`: aggressive limit (e.g., 3 requests per hour per email/IP).
- `POST /auth/reset-password`: limit on invalid-token attempts, to make brute-forcing the token harder.

### Specs — Error cases to handle explicitly
```text
Unregistered email                    → generic response (no enumeration)
Invalid/nonexistent token              → generic error
Expired token                          → clear message + option to request a new one
Already-used token                     → generic error (treated as invalid)
New password fails the policy          → validation error (Phase 1)
Multiple consecutive requests          → rate limit, visible cooldown
Successful reset                       → invalidates old sessions + notifies by email
```

- [x] Add `passwordChangedAt` to the `User` model (migration)
- [x] Implement `POST /auth/forgot-password` with a generic response and consistent response time
- [x] Implement random token generation + hashing before persisting
- [x] Implement `POST /auth/reset-password` (token validation, expiration, single use, new password via the shared schema from Phase 1)
- [x] Implement invalidation of previous reset tokens when a new one is generated
- [x] Implement updating `passwordChangedAt` on a successful reset
- [x] Update the authentication middleware to reject JWTs issued before `passwordChangedAt`
- [x] Implement rate limiting on `forgot-password` and `reset-password`
- [x] Create the "Reset your password" email template
- [x] Create the "Your password was changed" email template (security notification)
- [x] Create the "Forgot password" frontend page (email form)
- [x] Create the "Reset password" frontend page (`/reset-password?token=...`) with new-password validation (reusing the strength indicator from Phase 1)
- [x] Write tests: full successful reset flow
- [x] Write tests: expired token
- [x] Write tests: already-used token
- [x] Write tests: invalid token
- [x] Write tests: weak new password is rejected

### Completion criteria

## Phase 5 — Change Password and Change Email (Authenticated)

> ⚠️ Critical phase. Unlike Phases 3 and 4 (which assume the user has lost access), this phase assumes the user **is authenticated** — which brings a different risk vector: a compromised session (e.g., stolen device, XSS) being used to permanently hijack the account.

### Objective
Allow an authenticated user to securely change their password or their email, with current-password confirmation in both cases, and a security notification whenever the primary contact email is changed.

---

### 5.1 — Change Password

### Specs
- Requires the **current** password as confirmation (even with an authenticated session) — prevents a stolen session from changing the password without knowing the original secret.
- New password validated by the shared schema (Phase 1) and must be **different** from the current one.
- Endpoint: `POST /account/change-password` — body `{ currentPassword, newPassword }`.
- On success: update `passwordChangedAt` (reusing the mechanism from Phase 4), which automatically invalidates all other sessions/JWTs.
- Product decision: the **current** session (the one that made the request) should remain valid after the change — avoid logging the user out at the exact moment they complete the action. Other sessions (other devices) should be invalidated.
- Send a security notification email ("Your password was changed").

### 5.2 — Change Email

### Specs — Data model

```prisma
model EmailChangeToken {
  id           String   @id @default(uuid())
  userId       String
  newEmail     String
  tokenHash    String   @unique
  expiresAt    DateTime
  createdAt    DateTime @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
}
```

### Specs — Flow
1. The authenticated user requests an email change, confirming their current password.
2. `POST /account/change-email/request` — body `{ currentPassword, newEmail }`.
3. The email does **not** change immediately. An `EmailChangeToken` is created associated with the intended `newEmail`, expiring in **1 hour**.
4. A verification email is sent to the **new** address, with a confirmation link.
5. A **security alert is sent simultaneously to the old email**, informing them an email change was requested, with instructions on how to cancel/report it if it wasn't the account owner.
6. Only when the user clicks the link sent to the **new** email does the change take effect: `POST /account/change-email/confirm`.
7. On confirmation: the user's `email` is updated to `newEmail`, `emailVerified` remains `true` (the new email was already verified through this very flow), the token is invalidated; it's also recommended to invalidate other sessions for security (same logic as any other "sensitive account change").

### Specs — Handling an email that already exists
Since the user is already authenticated, there isn't the same third-party account enumeration risk that exists at registration/login — but it should still not directly confirm "this email already belongs to another account" in a way that lets an authenticated attacker probe the user base in bulk.
Recommended approach: if `newEmail` already belongs to another account, respond with a generic success message ("if the request is valid, you'll receive a confirmation email") **without** creating the token or sending any email — from the user's perspective, the request looks accepted, but nothing happens because the email is already in use. This avoids mass-enumeration side channels via this authenticated endpoint.

### Specs — Cancellation
- Endpoint `DELETE /account/change-email/cancel` — allows canceling a pending change request (e.g., if requested by mistake, or by the legitimate user after seeing the alert on the old email and realizing it wasn't them).
- The alert sent to the **old** email must include a direct link to cancel the request, even without logging in (its own single-use token).

### Specs — Error cases to handle explicitly
```text
Incorrect current password                         → clear error
New email equal to the current one                  → validation error
New email already in use by another account         → generic response (no confirmation), no email sent
Confirmation token expired                           → clear message + need to repeat the request
Confirmation token already used                       → generic error
Multiple consecutive change requests                   → only the most recent token is valid; previous ones invalidated
Cancellation via the old email's link                  → invalidates the pending token, confirms cancellation
```

- [x] Implement new-email uniqueness check with a generic anti-enumeration response
- [x] Implement token generation + hashing before persisting

- [x] Implement `POST /account/change-email/confirm` (finalizes the email change)
- [x] Implement `DELETE /account/change-email/cancel` (authenticated cancellation)
- [x] Implement cancellation via a single-use link sent to the old email (no login required)

## Phase 6 — Account Soft-Delete with a 15-Day Recovery Window

> ⚠️ Critical phase. A mistake here can result in irreversible, premature data loss, or, at the opposite extreme, "zombie" accounts that are never actually deleted. Both paths (recovery and final deletion) need explicit automated tests.

### Objective
Allow a user to delete their account, but with a 15-day grace period during which they can fully recover it, before a definitive, irreversible deletion of all their data.

### Specs — Data model

```prisma
enum UserStatus {
  ACTIVE
  PENDING_DELETION
}

model User {
  // ... existing fields
  status              UserStatus @default(ACTIVE)
  deletionRequestedAt DateTime?
  scheduledDeletionAt DateTime?
}

model AccountDeletionToken {
  id        String   @id @default(uuid())
  userId    String
  tokenHash String   @unique
  expiresAt DateTime
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
}
```

### Specs — Deletion request flow
1. The authenticated user requests account deletion in settings, confirming their current password.
2. `POST /account/delete` — sets `status = PENDING_DELETION`, `deletionRequestedAt = now()`, `scheduledDeletionAt = now() + 15 days`.
3. An `AccountDeletionToken` is generated (random, hash persisted, expires at `scheduledDeletionAt`).
4. A confirmation email is sent immediately: *"Your account will be permanently deleted on [date]. If you change your mind, click here to cancel."* — with a single-use recovery link.
5. All of the user's active sessions are invalidated immediately after the request (for security — forces a fresh login for any action, including recovery itself).

### Specs — Behavior during the grace period
- The user **can still log in** during the 15 days — this is essential to allow recovery even if they've lost the confirmation email.
- However, when logging in with a `PENDING_DELETION` account, the user does **not** see the normal application. They're redirected to a dedicated recovery screen: *"Your account is scheduled for deletion on [date]. Want to cancel?"* with a clear "Recover account" button.
- No other application functionality is accessible while the state is `PENDING_DELETION` — a dedicated middleware intercepts every protected route and redirects to the recovery screen.
- The account and its data remain intact in the database throughout the entire period — nothing is deleted until the 15 days are up.

### Specs — Recovery

**Via normal login** (the user is able to authenticate):
`POST /account/cancel-deletion` (authenticated) → same effect as Path A, available from the post-login recovery screen.

Both paths must be idempotent: recovering an already-active account should not produce an error.

### Specs — Reminders during the grace period (optional, but recommended)
Send email reminders partway through the period, to reduce accidental/unwanted final deletions:
```text
Day 0   → deletion request confirmation email (mandatory)
Day 7   → mid-period reminder (optional)
Day 14  → last warning, 1 day before final deletion (optional, but strongly recommended)
```

### Specs — Final deletion (scheduled job)
- A daily job (e.g., a GitHub Actions scheduled workflow, or a Render Cron Job, hitting a protected internal endpoint, or running a `pnpm run jobs:process-account-deletions` script) checks all accounts with `status = PENDING_DELETION` and `scheduledDeletionAt <= now()`.
- For each eligible account, **in this order**:
  1. Send the final email: *"Your account and all your data have been permanently deleted."* (must be sent **before** deletion, since the email will no longer be available afterward).
  2. Permanently delete the user (`prisma.user.delete`), which cascades (via the `onDelete: Cascade` already defined in the schema) to all associated Pillars, Habits, Completions, Goals, Projects, Tasks, and Daily Logs.
  3. Record an audit event of the deletion **without personally identifiable data** (e.g., just `{ userIdHash, deletedAt }`), for operational traceability.
- The job must be **idempotent**: if it runs twice on the same day (e.g., due to failure and reprocessing), it should not error out or try to delete an already-deleted user.
- Explicitly **do not** build a dedicated queue/worker infrastructure for this — a simple, direct cron job is sufficient and more aligned with the "no overengineering" philosophy already adopted in the project.

### Specs — Note on data isolation during the grace period
Although the user themself is blocked from the application while `PENDING_DELETION`, it's important to explicitly confirm that **no other user** can, directly or indirectly, access this account's data during the grace period (LifeOS's data model is already multi-tenant isolated by `userId`, but it's worth reconfirming in this phase, given this is a new state machine on top of `User`).

### Specs — Error cases to handle explicitly
```text
Incorrect current password when requesting deletion    → clear error
Duplicate deletion request (already PENDING_DELETION)  → clear error/idempotency ("already scheduled for X")
Invalid recovery token                                  → generic error
Expired recovery token (after the 15 days)              → account has been/will be deleted; inform appropriately
```

## Phase 7 — Internationalization (i18n) System

### Objective
Make the entire LifeOS interface translatable, with initial support for Portuguese, English, and Ukrainian, selectable via a dropdown in the profile, with no remaining hardcoded strings, and production-ready — including correct pluralization, locale-aware date/number formatting, and persistence of the choice across sessions and devices.

### Specs — Library and structure
- `i18next` + `react-i18next` on the frontend (industry standard, with good pluralization support via ICU/CLDR rules).
- File structure organized by language and functional domain:

```text
apps/web/src/i18n/
├── locales/
│   ├── en/
│   │   ├── common.json
│   │   ├── auth.json
│   │   ├── dashboard.json
│   │   ├── habits.json
│   │   ├── goals.json
│   │   ├── settings.json
│   │   └── errors.json
│   ├── pt/
│   │   └── ... (same structure)
│   └── uk/
│       └── ... (same structure)
└── index.ts
```

### Specs — Default language and detection
- Automatic browser language detection (`navigator.language`) on first access, falling back to English if the detected language isn't supported.
- The user's manual choice always takes priority over automatic detection, once set.
- Before login: preference stored in `localStorage`.
- After login: preference synced to the backend (`User.locale`) and used on any device the user logs into.

### Specs — Data model

```prisma
model User {
  // ... existing fields
  locale String @default("en")
}
```

### Specs — Language selector
- Dropdown in **Profile/Settings**, as requested, with flags/native names for the languages (e.g., "Português", "English", "Українська").
- Language change applied **instantly** in the interface, with no page reload.
- Persisted immediately to the backend (`PATCH /users/me` or an equivalent settings endpoint) and to `localStorage`.

### Specs — Pluralization (special attention to Ukrainian)
English and Portuguese have simple plural rules (singular/plural). **Ukrainian has complex plural rules** (categories `one`, `few`, `many`, `other`, depending on the number). i18next natively supports this via CLDR, but the `uk` translation files **must** define all plural forms correctly — not just one "generic" form. Conceptual example:

```json
{
  "habit_streak_days_one": "{{count}} день",
  "habit_streak_days_few": "{{count}} дні",
  "habit_streak_days_many": "{{count}} днів",
  "habit_streak_days_other": "{{count}} дня"
}
```

Recommendation: Ukrainian translations should be reviewed by a native speaker or a professional service, precisely because of this complexity — an automated translation risks getting the plural forms wrong.

### Specs — Date and number formatting
- Use the `Intl` API (`Intl.DateTimeFormat`, `Intl.NumberFormat`) or i18next's own formatting helpers, respecting the active `locale`, everywhere the app already shows dates (habit history, streaks, calendar, daily logs) or numbers/percentages (completion rate, statistics).

### Specs — Full coverage (zero hardcoded strings)
- Systematic audit, module by module, of the entire interface: authentication, onboarding, dashboard, habits, goals, projects, daily logs, analytics, settings, error messages/toasts, empty states.
- No string visible to the user should be written directly inside a component — everything must come from a translation key.
- Fallback: if a key doesn't exist in the active language, fall back to English (never show a raw key, e.g. `habits.title`, to the end user in production).

### Specs — Document `lang` attribute
The `lang` attribute on the `<html>` tag must update dynamically whenever the language changes, for accessibility (screen readers) and SEO reasons.

### Specs — Localized emails (tied to Phases 2–6)
The email templates created in Phases 2 through 6 should ideally respect the user's `locale` at send time (e.g., a user with `locale = "pt"` receives the verification email in Portuguese). A dedicated translation namespace for emails is recommended, reusing the same `i18next` infrastructure server-side (`i18next` also runs in Node.js, not just the browser).

### Specs — Ongoing quality
- A verification script (integrated into CI) that compares existing keys between `en`, `pt`, and `uk`, failing the build if any key is missing in one of the languages.
- Avoid "orphan" translations (keys defined but never used in the code) — the same script can flag this as a warning.

## Cross-Cutting Security Principles

These principles apply to **all** account management phases (3 through 6) and should be reviewed as a final checklist before considering v1.6 ready:

- [ ] No token (verification, reset, email change, deletion) is stored in plaintext in the database — only the hash.
- [ ] All tokens are single-use and invalidated after use.
- [ ] All tokens have an explicit expiration appropriate to the sensitivity of the action.
- [ ] No account-related endpoint reveals whether an email exists in the system (registration already meets this; reset, verification, and email change must follow the same pattern).
- [ ] Every sensitive account change (password, email, deletion) triggers an email notification to the relevant address(es), even when the action was legitimate — it acts as a safety net.
- [ ] Every sensitive account change invalidates outdated sessions/JWTs, preserving only the session that performed the action, where applicable.
- [ ] All account management endpoints have rate limiting appropriate to their sensitivity.
- [ ] No password, plaintext token, or sensitive data is ever written to logs, even on error.

## Recommended Execution Order

```text
Phase 1 — Strong Password Policy
        (foundation for the following phases)
Phase 2 — Transactional Email Infrastructure
        (technical prerequisite for Phases 3–6)
Phase 3 — Email Verification
Phase 4 — Password Recovery
Phase 5 — Change Password and Change Email
Phase 6 — Account Soft-Delete (15 days)
Phase 7 — Internationalization (i18n) System
```

Phases 1 and 2 are technical foundations for everything else and should be done first. Phases 3 through 6 share the same security pattern (random token + hash + expiration + single use + notification) and benefit from being implemented in sequence, reusing the same infrastructure. Phase 7 (i18n) is technically independent from the rest, but was left for last because it ideally also localizes the email templates created in the earlier phases — doing it last avoids rework.
